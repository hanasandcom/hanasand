# Security Scanner

The dashboard has distinct safe HTTPS checks, container-image findings from Trivy/Docker Scout, and authorized host assessments. A multi-asset assessment records its selected assets and engines as individual jobs, reconciles each job with its provider, and reports partial failures separately. Keep each source and its coverage visible; a combined automated assessment is still not a complete penetration test.

## Network inventory

An owner or editor registers a hostname in **Dashboard → Security Scanner**. The API creates a DNS TXT challenge at `_hanasand-security-verification.<hostname>`. The asset becomes eligible for scanning after DNS control is verified. Hanasand resolves the verified name immediately before each run, rejects private or otherwise non-public IPv4 addresses, and limits the scope to five addresses.

The initial engine is Nmap's `tcp-top-100` profile. It uses TCP connect probes, light service/version detection, a maximum rate of 25 probes per second, a per-host timeout, a total run timeout, and an 8 MiB XML result cap. It does not run NSE scripts, UDP probes, operating-system detection, or web crawling. Results are service observations with the engine version, timestamps, coverage counts, and a SHA-256 digest of the raw XML. They must not be presented as confirmed vulnerabilities.

Before a manual scan or recurring schedule can run, an owner/editor confirms authority over the asset and its currently resolved IP addresses. Hanasand stores that address set with the authorization. If DNS changes the set, a scheduled run is paused and the address scope must be confirmed again. Recurring schedules support intervals from 5 to 1,440 minutes; the scheduler queues at most one due run each minute.

## Service boundary

The Hanasand API is the authenticated website BFF: it owns identity, organization roles, entitlement checks, billing quotas, and audit events. The standalone [Scanner service](https://github.com/hanasandcom/scanner) owns UVM assets, DNS verification challenges, authorized address sets, schedules, assessments, engine credentials, run history, findings, and triage. The API forwards organization-scoped requests over the private service connection. Configure `HANASAND_SCANNER_URL` and the same random `HANASAND_SCANNER_SERVICE_TOKEN` in both server environments; the token never reaches the browser. Only `GET /health` is unauthenticated; other Scanner routes require the service token.

Schedules and provider jobs now run in Scanner. The Hanasand API no longer creates or advances UVM domain tables on startup. Legacy UVM tables are retained unchanged for migration and rollback; do not drop or rewrite them during cutover. The one-time transfer uses `api/scripts/migrate-uvm-data-to-scanner.ts` against the configured target, imports a repeatable snapshot, and leaves every source row in place. Run it against staging first, compare imported counts and dashboard history, then use the explicit production cutover flag only during a coordinated release. For rollback, restore the previous API and Scanner revisions while retaining both databases; do not run the importer again with modified source data under the same migration ID.

## Tenable Vulnerability Management

An owner or editor can connect an existing Tenable Vulnerability Management account by selecting its cloud region and entering API keys on the Scanner page. Hanasand sends the credentials to Scanner over the private service connection; Scanner stores them per organization with AES-256-GCM encryption. Set `SCANNER_CREDENTIAL_ENCRYPTION_KEY` to 64 hexadecimal characters in the Scanner environment before connecting an account. Scanner checks the keys against the selected Tenable cloud region and lists enabled scan configurations. Each run selects one configuration and submits only the asset's currently authorized public IPv4 addresses as alternate targets. This is a Tenable VM cloud integration that launches enabled Nessus scan configurations; it is not a direct connector to a standalone Nessus Pro host. Tenable's [Nessus documentation](https://docs.tenable.com/nessus/10_12/Content/PDF/Nessus_10_12.pdf) says direct access to Nessus scanning APIs to configure or launch scans is only permitted as part of Tenable Security Center or Tenable Vulnerability Management enterprise solutions.


Scanner runs launch asynchronously, poll Tenable for completion, and import the Nessus report export. Findings retain the Tenable plugin ID, CVEs, CVSS data, affected address, evidence, and first/last-seen timestamps. Scanner filters findings to the requested addresses and reports requested, reported, and missing addresses; truncated, error-bearing, or missing-host exports remain partial. The Hanasand findings queue stores source-specific records and supports open, in-progress, pending-verification, accepted-risk, false-positive, and resolved statuses. Accepted risk and false-positive decisions require a triage note. Only a successful report covering every requested address can resolve findings that disappear. Users mark remediation as pending verification; a later complete scan confirms resolution.

## Greenbone Vulnerability Management

When the Scanner service is configured with a private Greenbone Manager endpoint and valid TLS credentials, it enables GVM only after checking manager access, the fixed Full and Fast scan configuration, the OpenVAS scanner, the operator-selected port list, and loaded NVT/SCAP/CERT/GVMD_DATA feeds. Hanasand sends only the selected asset's authorized public IPv4 addresses; client requests cannot supply a manager URL, config, scanner, or port-list ID. The GMP worker creates and deletes its own targets/tasks, polls asynchronously, imports findings only for requested addresses, and records report-host coverage. GVM is on-demand only; recurring GVM schedules are not supported. Live manager and feed compatibility still requires deployment validation.

Assessment history, findings, and scan schedules are stored by Scanner after cutover. Keep the previous Hanasand UVM tables as a read-only rollback copy until the migration has been verified and the retention decision is made separately.

The network worker runs separately from the image scanner and has no Docker socket. It needs outbound access to approved public scan targets and the private Scanner database network. Keep both service and database off public interfaces. The service supports one Nmap worker replica, reports worker heartbeat, and marks a running job failed if the worker restarts.

## Current boundaries

Nmap provides service inventory; it does not confirm vulnerabilities. Tenable VM and GVM provide vulnerability assessments when their providers are configured and ready. Standalone Nessus is not connected. Web-check warnings enter the UVM queue and a later passing check resolves that specific warning; passing checks remain available in the safe web report. Container-image findings still use their own report view. Findings do not yet have a remediation owner or due date. Scanner output is not a comprehensive penetration-test result, and incomplete engine coverage must never be presented as a clean assessment.
